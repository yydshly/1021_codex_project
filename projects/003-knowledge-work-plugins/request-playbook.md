# 以后提出类似需求时的参考手册

本页是基于上游工作流整理的**原创需求模板和本研究建议**，不是上游原文，也不是必须安装插件才能使用的命令。方括号替换成自己的信息；删掉与任务无关的部分即可。参考依据见 [工作流](workflows.md) 和 [约束类型](constraints.md)。

本页保留简版模板。2026-10-21 新增的 [逐业务分析](business-analysis.md) 提供详细输入检查、控制责任、异常、审批与验收；[网页](web/index.html) 构建时将这些补充合并到对应模板和流程草稿，可直接编辑复制完整版。无需逐字照搬，按本组织实际规则和已授予权限调整。

## 先选择任务，再补齐要求

1. 在 [角色地图](roles.md) 找与你的目标最接近的业务，不必拘泥于自己的岗位。
2. 在 [全量索引](scenario-index.md) 定位具体任务，优先看触发条件和所需输入。
3. 参考 [代表流程](workflows.md)，决定需要“分析 / 草稿 / 可下载文件 / 实际系统操作”中的哪一种。
4. 写明需要的证据、范围、权限和交付标准。复杂任务可以分阶段；简单任务不必使用完整模板。
5. 用一个真实小任务验证效果，再考虑固化为 Skill 或自动化。

## 通用任务卡

```text
目标：帮助[谁]完成[业务任务]，结果用于[决策/执行/沟通]。
范围：[对象、时间段、系统、需要处理的记录]。
输入：[文件/链接/数据/背景]；优先事实来源为[来源]。
公司规则：[指标口径、品牌规范、审批规则、行业要求]。

执行：
1. 先检查已有输入与工具，识别影响结论的缺失项。
2. 按[步骤]工作；关键缺口先询问，一般缺口注明假设后继续。
3. 区分事实、推断和建议，关键结论附来源与时间。
4. 遇到[失败/冲突/权限拒绝]时，按[降级或停止规则]处理。

权限：本次允许[只读/生成本地文件/指定系统指定写入]。
如需确认，应展示明确的[对象、修改前后、收件人、金额等]。
交付：[格式、结构、保存位置、必需字段]。
验收：[可以复算、查看、执行或复核的判据]。
最后列出已完成、未验证和仍需我决定的事项。
```

对低风险的一次性任务，可以缩短为：

> 根据[资料]完成[任务]，用于[用途]。按[关键步骤]处理，遵循[两三条重要约束]，交付[具体格式]，并用[方法]检查结果。关键资料缺失时指出缺口。

## 12 个可直接改写的场景模板

### T01 · 客户会议 / 合作伙伴会前准备

> 为我准备[日期、时间、客户]的会议。根据[客户资料、历史纪要、邮件、商机记录]，整理参会人、当前进展、此前承诺、未闭环问题和本次会议目标。关键事实附来源和日期，区分没查到与确认没有。交付一页简报和 5 个优先问题。本次仅准备材料，不发送消息或修改记录；缺少会议时间或客户身份时先确认。

对应 W01；也适用于供应商谈判、项目评审、内部汇报。

### T02 · 客户问题分诊与回复

> 对[工单集合]按我提供的[类别、优先级、SLA、队列规则]分诊。先提取症状和影响，再检查已知问题、重复工单和替代方案。交付类别、优先级理由、推荐负责人、首轮回复草稿和升级条件。没有查询权限的系统标“未查”，不要承诺未确认的修复时间。请将实际已执行动作和建议动作分开。

对应 W02；公司规则缺失时可先给一份待确认的分类方案。

### T03 · 将模糊想法转为 PRD

> 把[问题/想法]整理为供[研发/设计/业务方]评审的 PRD。先明确目标用户、问题证据和成功指标，再定义目标、非目标、P0/P1/P2、依赖和分期。每项 P0 附正常、失败及边界情况的验收条件。没有依据的目标数值标为假设；开放问题注明责任方和是否阻塞。

对应 W03；适用于新功能、流程改造或内部工具需求。

### T04 · 文案与品牌审查

> 依据[品牌手册、术语表、已批准信息]审查[文案]，受众是[人群]、渠道是[渠道]。输出问题位置、依据、严重程度和修改建议，并给出重要段落的修改前后对照。对无法证明的最高级、数据和竞品比较单列问题；没有品牌依据时说明只做通用质量检查。交付可编辑稿，不发布。

对应 W04；适用于官网、活动、销售材料和客户通知。

### T05 · 合同 / 供应商条款审查准备

> 从[我方身份]出发，依据[公司立场手册]审阅[合同及附件]。说明已读范围，比较关键条款、公司标准、偏差和商业影响，给出谈判优先级、修订建议与升级事项。缺附件、法域或立场规则时指出缺口，不把通用规则冒充公司要求。交付供[法务/采购]复核的意见表，本次不签署或发送。

对应 W05，也可结合运营 `vendor-review`。这是需求组织模板，不是法律结论。

### T06 · 对账与差异清单

> 核对[实体、币种、截止日]的[总账]与[银行/明细账]，按[公司口径]处理。先检查范围一致性、重复和缺失，再列出每个差异的来源、金额、原因分类、账龄、建议处理与责任人。无法解释的差额保留，不为凑平编造调整。交付可复算底稿、建议分录和待复核清单；本次不实际过账。

对应 W06；财务阈值由本公司的规则确定。

### T07 · 指标异常分析与看板

> 分析[指标]在[时间范围]的变化，按[渠道/产品/地区]拆分。定义口径、分母、粒度和对比基线，检查重复、空值与缺失周期；保留查询或计算步骤。输出主要发现、支持证据、其他可能解释及下一步验证。若生成看板，注明数据日期和更新方式；我要求[联网/离线]打开，请实际验证筛选和总数一致性。

对应 W07；“为什么下降”应区分描述性拆分与经过验证的原因。

### T08 · 设计审查与研发交付

> 评审[设计稿/页面]的[核心用户任务]，重点检查层级、文案、状态、边界和[指定规范版本/级别]。将视觉证据与实际交互测试分开；没有测试键盘或读屏就标未验证。输出问题位置、影响、优先级和修复建议，并整理开发需要的状态、规则、组件与验收清单。

对应 W09，也可结合 `design-handoff` 与 `ux-copy`。

### T09 · 故障 / 延期复盘

> 根据[任务记录、日志、会议纪要、沟通材料]复盘[事故/延期]。先还原计划、实际进度和关键时间线，再区分已证实原因、合理假设、矛盾材料与证据缺口。交付影响、已采取措施、待验证原因和带责任人 / 截止日 / 完成判据的改进行动。关注系统和流程，不以猜测归责个人；本次仅整理材料。

对应 W10、W15；延期复盘是本研究迁移案例，不宣称上游有一个同名完整流程。

### T10 · 人员反馈 / 入职与绩效材料

> 按[角色、考核周期、公司标准]整理[人员工作事实]，输出有具体行为证据的贡献、发展项和下一阶段行动。区分本人贡献与团队成果，不补造事件，不以模板比例代替公司评价规则。只使用[允许范围]内资料，先形成由[负责人]复核的草稿，再决定是否写入人员系统。

对应 W11；若是入职任务，将交付改为责任人、日期、材料和完成检查表。

### T11 · 流程 / 系统变更申请

> 为[变更]编写申请，说明动因、受影响用户和系统、风险、成本、依赖和实施窗口。交付步骤、责任人、沟通对象、审批事项，以及回滚触发条件、操作与恢复验证。审批状态按实际证据填写；本次允许[生成草稿/创建指定变更单]，实际执行另按授权范围处理。

对应 W12；适用于上线、迁移、供应商切换和组织流程变更。

### T12 · 将重复工作整理为可复用流程

> 把我每[周期]进行的[任务]整理成可复用工作流。先记录触发条件、输入、事实来源、步骤、工具、写入范围、异常处理、交付格式和验收。区分单次运行与调度配置，列明首次运行要补的背景。用一个小样本验证后，交付[任务卡/Skill 草稿/插件方案]，不要把模板完成当作自动化已经上线。

对应 W13、W14、W16；需要 PDF 或专业科研时再补 W17、W08 的具体环境和文件验收。

## 跨岗位组合：如何提出一个更大的业务需求

以下是本研究设计的组合，不是上游已经实现的一键端到端流程。

### 例 A · 为什么客户续约率下降

```text
数据：明确续约口径和下降发生在哪些客户群
  → 客服：归纳工单、投诉和未解决问题
  → 销售：核对账户变化、商机与续约记录
  → 产品：将证据转成待验证的改进机会
  → 经营报告：结论、替代解释、优先行动与负责人
```

提出需求时补充：时间窗、客户去重键、续约分母、主数据源、可访问材料。验收要求跨系统客户能对齐，相关性不能直接表述为因果；最终报告区分分析结果与实际触达动作。

### 例 B · 发布新功能

```text
产品：PRD、范围和验收
  → 设计：状态、文案、无障碍与交付
  → 研发：测试、部署准备和回滚
  → 营销：发布材料与品牌审查
  → 客服：知识文章和问题分诊准备
```

提出需求时明确：同一功能版本、发布对象、禁用承诺、审批人、上线窗口和已完成证据。文档准备完成与代码上线、文案发布应分别记录状态。

### 例 C · 开源项目研究（适合本仓库）

```text
发现项目 → 固定 Commit 与许可证
  → 梳理能力、角色与场景
  → 追踪入口、执行步骤和依赖
  → 选择代表任务验证
  → 记录事实、局限和需求参考
  → 更新项目索引并运行仓库检查
```

可直接使用：

> 按本仓库约定研究[上游 URL]。先固定版本和许可证，再整理角色、业务、输入、执行步骤、约束、交付和验收。全量清点入口，深入阅读代表实现，区分文档承诺、静态事实和实测结果。没有环境或凭据的部分标未验证。将可迁移的方法改写为需求模板，保存证据链接与复现步骤，并更新项目索引。

## 何时直接对话，何时固化

| 情况 | 建议形式 | 理由 |
| --- | --- | --- |
| 一次性、资料齐全、没有复杂工具动作 | 简短对话需求 | 固化成本可能高于收益 |
| 同类工作频繁重复、格式稳定 | 任务卡或 Skill | 复用步骤、边界和格式 |
| 多人共享同一流程、多个工具接入 | 定制插件 | 集中维护规则与配置 |
| 要按时触发、无人值守 | Skill 加宿主调度与权限控制 | 仅有 Skill 不会自动持续运行 |
| 金额、人员、生产系统等高后果写入 | 明确授权与系统层控制 | 文本约束不足以提供强制保证 |

## 最小效果验证方案（待执行）

同一模型、同一输入、相同工具权限下比较两组：A 使用目标明确的普通需求，B 使用整理后的工作流。可以另设 C 组，将同等详细流程直接写进对话，区分“内容更完整”的收益与“插件包装”的收益。

至少用正常、缺信息、来源冲突、权限拒绝四类样本；每次记录输入版本、模型 / 宿主 / 插件版本、执行耗时、人工补充次数、事实错误数、遗漏验收项、越权动作和返工时间。权限相关测试用沙箱或模拟工具。

本次没有运行这些对照实验，所以不提供效率提升百分比或正确率结论。只有当结果更完整、补充更少且额外检查成本可接受时，才能说该流程对你的业务有实际收益。
