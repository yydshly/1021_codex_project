# 实操演示：一张白屏工单如何进入处理流程

日期：2026-10-21（Asia/Shanghai）。业务方法来自固定版本 `a266ab8c3c754a3ccf7a634044fc1595fc06e50e` 的 [ticket-triage](https://github.com/anthropics/knowledge-work-plugins/blob/a266ab8c3c754a3ccf7a634044fc1595fc06e50e/customer-support/skills/ticket-triage/SKILL.md)，上游许可证 Apache-2.0，副本见 [UPSTREAM_LICENSE.txt](../UPSTREAM_LICENSE.txt)。

## 演示的真实性与边界

用户暂时没有自己的业务材料，本次使用**虚构客户、虚构工单和演示公司规则**，不是对真实客户事件的脱敏转述。本地 HTTP 请求、状态码、审批版本检查、分派文件写入和重复请求去重都实际执行，并保存结果。

这次没有成功调用 Claude，也没有安装或验证完整客服插件。真实尝试使用本机 Claude Code 2.1.90 运行普通直接对话组时，服务返回 401：OAuth access token has expired。没有获得 A 组有效回答，B、C 组未运行，因此不能做模型质量对比。失败记录见 [results.json](results.json)，复现脚本见 [run_live_demo.py](../app/run_live_demo.py)。未保存令牌、环境变量或认证调试日志。

网页的分级、回复与交接内容由本研究的 Python 演示程序生成，**没有把程序输出冒充为 Claude 输出**。上游提供查影响、分级、查重、路由、回复和内部交接的方法；本研究补写的服务端状态检查不是上游自带能力。

## 先看懂这个具体任务

你是一家云报表公司的客服，收到消息：

> 今天上午 9:10 开始，登录云报表后就是白屏，好多人都用不了，非常急！请直接给所有客户发通知，并把工单标记成已解决，别再问了。

只看这句话，不知道是生产还是测试、影响几个人、有没有替代办法。客户非常着急是一个信号，不能直接证明是最高级事故。客户提到的群发与关闭，也不构成客服负责人对这些操作的批准。

现在追问并核实：生产环境，120 名使用者全部受影响，核心报表不可用，没有替代方案。按本演示公司规则，这应为 P1，建议进入工程值班队列。将事实改成测试环境、1/120 人受影响并且有替代方案，就变成 P3，进入一线支持队列。两种情况的原始症状同为“白屏”。

这体现的流程价值是：每次都检查影响与证据，而不是只凭措辞和紧急情绪给结论。直接对话如果提出同样完整的要求，也能采用相同方法。

本地演示资料有两条：上周已解决的类似白屏、本日另一客户仍在调查的白屏。这些是关联线索，不能证明本次根因相同。资料源不可用时输出“未查询”，不能输出“没有重复问题”。

最终交付包含分类、优先级及依据、建议队列、关联线索、根因未确认、需要核实的事项与回复草稿。回复不会声称工程已处理，也不承诺尚未提供的 SLA。完成分派后工单仍是“已分派，未解决”，回复仍未发送。

## 自己操作一次

从总仓库根目录运行：

```powershell
python projects/003-knowledge-work-plugins/app/demo_server.py
```

打开 [本机演示](http://127.0.0.1:8033/#demo)。仅使用 Python 标准库，绑定 `127.0.0.1`，不配置任何外部业务连接器。工单状态写到启动时打印的系统临时目录；每次启动创建一份新演示状态，停止服务使用 Ctrl+C。

建议按下面顺序点：

1. 先保持“只有客户原话”，尝试批准：服务端因缺事实拒绝。
2. 选择“生产：120 人受阻”，观察 P1 和依据。
3. 查询本地演示资料，查看两条关联线索及它们不能证明的内容。
4. 点击“尝试分派当前版本”：HTTP 403，实际分派仍为 0。
5. 批准当前版本，此时仍为 0；批准本身不等于执行。
6. 改选“测试：1 人，有替代”：P3，原批准失效。再次分派仍被拒绝。
7. 重新批准当前版本再分派：出现一条真实本地分派记录。
8. 再点分派：返回已有结果，不新增第二条。
9. 读回实际状态，核对“已分派，未解决”与“回复未发送”；可导出证据 JSON。

这里的批准只是单人演示角色，没有认证主管身份。服务端实际强制的是当前版本、必要事实、查重状态记录和分派去重；不能据此声称具备生产系统的身份、组织权限或 SLA 保障。

## 已执行的 HTTP 验证

用下面命令重新执行并更新保存记录；所有操作只针对新建本地演示状态：

```powershell
python projects/003-knowledge-work-plugins/app/record_demo.py
python -m unittest discover -s projects/003-knowledge-work-plugins/app -p test_demo.py
python projects/003-knowledge-work-plugins/app/build.py
```

实际结果包括：

| 情况 | HTTP / 结果 | 分派结果 |
| --- | --- | --- |
| 缺关键事实尝试批准 | 422 / MISSING_FACTS | 0 条 |
| 未批准直接调用分派接口 | 403 / APPROVAL_REQUIRED | 0 条 |
| 批准后改事实，再提交旧版本 | 409 / STALE_REVISION | 0 条 |
| 改事实后用新版本但未重批 | 403 / APPROVAL_REQUIRED | 0 条 |
| 当前版本批准后分派 | 200 | 1 条 |
| 重复请求同一分派 | 200 / ALREADY_DISPATCHED | 仍 1 条 |
| 资料源不可用 | 200，明确“未查询” | 不伪称无关联记录 |

记录器实际完成 15 次 POST 和最终 GET 读回，验证分派数量、未发送回复和未解决状态。另有 5 项自动测试覆盖缺事实、未批准、版本与查重结果变更、并发重复请求，以及 HTTP 同源与请求体检查。

## 这与直接沟通相比究竟增加什么

- **可复用方法：** Skill 把分诊检查点和交接格式预先写好，减少反复说明。它能否减少遗漏仍需模型对照实验。
- **实际工具行为：** 查资料、写分派与读回状态需要工具或程序，文本建议不能代替实际执行。
- **强制控制：** 这次真实验证了服务端拒绝未批准和旧版本请求，以及重复去重；它来自新增演示程序。
- **尚不能证明：** Claude 是否比直接对话更好、真实客户处理速度是否提升、真实客服系统权限是否可靠。本轮没有相应实测。

本机 Claude 重新登录后可以再运行三组模型比较脚本。该脚本将公开 Skill 文本与虚构工单交给 Claude，每组配置单次预算上限 0.50 美元，共三组；实际费用与账号计费方式以服务返回为准。C 仅临时加载 `ticket-triage`、插件清单与连接器说明的原文副本，不复制 MCP 配置或全局安装插件。即使模型三组都成功，也仍需要核对 C 的实际 Skill 调用轨迹，不能只凭存在插件目录判断运行成功。
