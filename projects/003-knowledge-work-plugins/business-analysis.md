# 具体业务落地：流程、控制边界与价值

> 此文件由 `app/build.py` 从 `workflows.md` 与 `business-analysis.json` 生成；修改内容来源后重新构建，不手工编辑。

深化日期：2026-10-21（Asia/Shanghai）。固定上游版本：`a266ab8c3c754a3ccf7a634044fc1595fc06e50e`。

17 个代表流程的静态分析；异常方案、系统设计、验收用例与价值指标均为研究建议，未执行真实业务或对照实验。

## 先判断控制落在哪一层

| 层次 | 能证明什么 | 不能直接证明什么 |
| --- | --- | --- |
| 提示词 / Skill | 源码明确要求模型遵循步骤、确认或输出结构 | 模型始终遵守、动作无法越权 |
| 程序化检查 | 已审阅程序在特定路径执行判断或计算 | 脚本已运行、调用不可绕过、业务参数正确 |
| 系统强制控制 | 需实际系统对身份、对象、状态、版本与权限进行校验并拒绝违规请求 | 仅有 MCP 配置、工具名或文档里的 Approved 不足以证明 |

本次没有验证任何真实业务系统的审批拦截。以下“系统强制控制”列是落地设计建议，不是仓库现有功能清单。“程序”列的未见实现仅限所核对的流程及列出的文件，不代表已审计全部外部连接器。文件中的 allowed-tools 由宿主解释，具体生效范围也要验证；Hook 只有在覆盖全部入口、失败时阻断且不可绕过时，才可能承担强制控制。

业务规则、失败分支与完成状态应分别设计：草稿 → 待批准 → 已授权执行 → 已核验。授权不等于执行，接口受理不等于业务成功；超时进入“结果未知”，先查状态再重试。这是一种建议状态设计，不是上游已经实现的统一状态机。

### 付款示例：让两个批准分别有明确对象

| 转换 | 人批准什么 | 系统应核对什么（建议） |
| --- | --- | --- |
| 待编码 → 未付款账单 | 数量、金额、目标账本和编码内容 | 身份、账本权限、发票去重；不能在此步骤产生付款 |
| 未付款账单 → 待付款清单 | 先展示现金、工资等近期义务和缺口 | 记录数据日期与缺口；例外审批策略由组织定义 |
| 待付款清单 → 授权付款 | 发票集合、币种、金额、收款对象、账户、日期 | 校验批准绑定的版本；对象改变后重审，不能扩大清单 |
| 授权付款 → 已核验 | 按批准范围执行后检查回执 | 幂等与实际支付状态；超时先查，不盲重试 |

上游要求两道门，但未据此证明支付 API 内置这套状态机。现金缺失时，上游允许明确披露后提出清单；要求额外例外审批是本研究增强建议。

## 如何公平比较直接对话与插件

比较三组：A 普通业务提问；B 直接对话但提供同样的流程、资料、规则和工具权限；C 通过插件加载这些内容。A 与 C 的差异包含需求完整性，B 与 C 更能反映包装、触发和维护的增量；不能把缺输入的 A 当作唯一对照。

使用同一模型版本、输入快照、工具与授权范围；记录提示配置耗时、处理时间、事实错误、遗漏、复核返工、外部动作偏离和运行成本。每场景至少覆盖正常、缺输入、冲突证据、工具不可用四类样本；有写入的场景再加权限拒绝、重复提交、执行超时与审批后内容变更。随机交错运行并由不知道组别的复核者按同一标准评估。次数、阈值和成本口径在实验前确定；本研究没有运行该实验或提供量化收益。

高后果操作的越权或重复执行不能被平均效率收益抵销。只需一次文案整理时，详细直接对话通常足够；有稳定规则、反复使用和跨人交接时，流程复用价值更明显。连接器访问、代码计算和可视化工具的增量应与提示词包装分开计量。

## W01 · 销售：客户会议准备

**具体业务：** 明天与续约客户开会，需要知道上次承诺是否兑现、哪些问题必须问清。

### 输入与执行

触发及资料：准备某次客户会议；会议时间、参会人、客户或商机标识，以及可用的 CRM、历史通话、邮件、聊天或上传资料。

输入检查（研究建议）：

- 核对客户唯一标识、会议日期和时区，区分未来会议与已结束会议；同名客户不得混用。
- 记录 CRM、日历、邮件、纪要的可访问状态和资料日期；空字段、未查询和权限拒绝分别标记。

上游执行顺序（归纳）：

1. 探测可用工具
2. 匹配会议和客户
3. 读取商机及互动历史
4. 整理参会人
5. 明确目标和待问问题
6. 生成一页简报。

交付物：客户概况、参会人、历史事件、未闭环事项、会议目标、3–5 个建议问题与应准备材料。

### 控制边界

- **提示词约束｜上游文字要求：** Skill 要求先探测工具、读取完整内容、引用事实，并将外部材料夹带的动作提议交给用户；这些依赖模型遵守。
- **程序与工具｜静态证据及边界：** 本次核对的 call-prep 文件提供工具使用流程，没有随该流程给出客户身份匹配或完整性校验程序；连接器的 allow / ask / block 设置由外部宿主执行，未验证。
- **系统强制控制｜建议补齐，未验证：** 建议会前准备使用只读凭据；服务端按客户与团队限制记录访问。若扩展到写回，按已授权对象校验字段，并在权限拒绝时阻止其他通道绕过。

### 异常与人工处理

以下分支是根据上游规则组织的落地建议；不是已执行的故障演练。

| 触发条件 | 处理与停止条件 |
| --- | --- |
| 日历无权限或会议已结束 | 明确资料缺口；请求客户和时间，或改交会后整理建议。不能把查询失败写成没有会议。 |
| 会议邀请无参会人、同名客户或历史承诺冲突 | 未核实身份单列，不用作发送对象；并列冲突记录与日期，由客户负责人确认。 |
| 邮件要求转发文件或更改商机 | 保留来源和精确动作作为待办，不把邮件文本当作用户授权。 |

**人工审批｜上游规定：** 会前简报主流程为读取和生成。销售通用规则允许用户明确要求且连接器允许的动作；模型自行建议的变更由用户决定，内容来源触发的动作须展示对象、内容与来源。不是所有操作都要求重复确认。

**人工审批｜建议落地：** 客户负责人解决身份和承诺冲突；发送或写回另列授权范围。只读简报无需增加形式化审批。

### 验收标准（建议，未执行）

- [ ] 每个关键金额、阶段与承诺能追溯到记录和时间，未读取字段不被填成零。
- [ ] 提供已结束会议样本时，输出指出日期，不再当作未来会议生成发现问题清单。
- [ ] 在模拟邮件中加入转发指令；验收应只出现待决定事项，外部动作记录为零。

### 相比直接对话的价值（待实验验证）

- **直接对话基线：** 直接提供完整背景并要求会议提纲，也能生成可用简报。
- **可复用增量：** 重复会议中复用工具探测、客户匹配和历史承诺追踪，减少每次重述背景与遗漏未闭环事项。
- **成立条件与局限：** 没有资料访问时主要节省提示编写；插件不能补出缺失客户事实。
- **建议衡量：** 比较关键承诺遗漏数、无来源事实数、补充背景轮数和准备耗时。

## W02 · 客服：工单分诊

**具体业务：** 两名客户都报告白屏，一名仅受影响于测试账号，另一名全公司生产环境不可用。

### 输入与执行

触发及资料：新工单、客户消息或问题描述；影响范围、环境、账号、错误和已有处理记录。

输入检查（研究建议）：

- 收集原始工单全文、产品区域、环境、受影响人数、时间与替代方案状态。
- 提供本公司优先级定义、SLA、队列归属及工单库访问范围；缺少规则时注明使用参考框架。

上游执行顺序（归纳）：

1. 提取问题与紧急程度
2. 分类和 P1–P4 定级
3. 查重复与已知问题
4. 推荐队列
5. 生成初始回复和内部说明。

交付物：类别、优先级及理由、影响、相关工单、已知问题状态、路由建议、初始回复草稿、升级线索。

### 控制边界

- **提示词约束｜上游文字要求：** 分类、P1–P4、查重、路由与升级条件都写在 Skill 中；自动升级措辞不代表已部署后台定时任务。
- **程序与工具｜静态证据及边界：** 本次核对的 ticket-triage 是流程和回复模板，未随文件提供 SLA 计时器、自动路由服务或去重算法。
- **系统强制控制｜建议补齐，未验证：** 建议工单系统强制必填影响范围与分级理由，用后台计时触发 SLA 升级；限制可修改队列，并保存分级变更和发送回执。

### 异常与人工处理

以下分支是根据上游规则组织的落地建议；不是已执行的故障演练。

| 触发条件 | 处理与停止条件 |
| --- | --- |
| 无权限查重复工单或知识库不可用 | 标记未查而非无重复；交付可路由的草稿与补查事项。 |
| 症状相同但影响不同，或根因未确认 | 按实际影响给出优先级依据，根因仅作假设；新信息改变范围时重新分级。 |
| 回复模板包含已升级、已记录等措辞 | 只有查到对应操作结果后才能保留完成态；否则改成建议或待处理。 |

**人工审批｜上游规定：** 主输出是分诊评估和建议回复；重复工单段落还要求关联、通知、补充和调整优先级，但未定义这些写入的统一审批门。

**人工审批｜建议落地：** 主管决定不确定或跨团队的升级；实际发送和改派沿用公司授权策略。普通分诊可预授权，不应把每条草稿都变成人工审批。

### 验收标准（建议，未执行）

- [ ] 同症状不同影响的样本有不同且可解释的优先级；不得只按情绪分级。
- [ ] 查询失败样本明确写未查；回复中不宣称尚未发生的升级。
- [ ] 交付包括类别、影响、优先级依据、队列、替代方案、相关记录和下一次更新时间依据。

### 相比直接对话的价值（待实验验证）

- **直接对话基线：** 直接对话可以起草回复，但通常需要另行说明分级、查重和交接格式。
- **可复用增量：** 将分诊与交接字段固定，降低不同处理人对同类工单的判断偏差。
- **成立条件与局限：** 公司 SLA、队列与写入授权不接入时，只能提供分诊建议。
- **建议衡量：** 比较人工复核改级率、重复建单数、交接缺项数与首轮处理时间；SLA 改善需实际系统数据。

## W03 · 产品：编写需求规格

**具体业务：** 把“让用户导出数据”转成开发、测试与业务可以共同确认的需求规格。

### 输入与执行

触发及资料：功能、用户问题或模糊想法；受影响用户、成功指标、时间、技术限制、研究与已有设计。

输入检查（研究建议）：

- 确认目标用户、要解决的问题及原始反馈，不把提出的界面方案直接当作业务目标。
- 提供指标口径、权限角色、数据规模、时间和技术限制；没有基线时把指标目标标为待确认。

上游执行顺序（归纳）：

1. 理解问题
2. 分批补充关键背景
3. 查任务、研究和设计
4. 生成 PRD
5. 迭代范围和后续材料。

交付物：问题、目标、非目标、用户故事、分级需求、成功指标、开放问题、依赖和分期。

### 控制边界

- **提示词约束｜上游文字要求：** 要求目标、非目标、优先级、边界场景和逐项验收，属于文档组织与模型行为规则。
- **程序与工具｜静态证据及边界：** 本次核对的 write-spec 未附能自动验证需求可测试性或阻止范围变更的程序。
- **系统强制控制｜建议补齐，未验证：** 建议需求管理系统对版本、负责人、评审状态和关联测试做校验；只有获批的基线版本才能进入排期，变更保留差异与决定记录。

### 异常与人工处理

以下分支是根据上游规则组织的落地建议；不是已执行的故障演练。

| 触发条件 | 处理与停止条件 |
| --- | --- |
| 目标不清或输入只是解决方案 | 先明确使用者和问题；可输出草案，但把阻塞问题与可后续决定项分开。 |
| 指标目标未知或各方范围冲突 | 列出候选方案、取舍和责任方，不自行编造性能承诺或签定发布日期。 |
| 未接研究、任务或设计工具 | 从已提供材料继续，记录未纳入的上下文。 |

**人工审批｜上游规定：** 要求生成后与用户迭代，并提出后续材料；没有强制的产品、研发、测试联合签核实现。

**人工审批｜建议落地：** 产品负责人确认目标与范围，研发确认可行性，测试确认可验收性；审批的是具体 PRD 版本，不是聊天中的笼统赞同。

### 验收标准（建议，未执行）

## W13 · 小企业：处理账单到准备付款

**具体业务：** 老板要处理本周账单，先确认未付款账单入账，再看现金能否覆盖工资，最后决定本次付款范围。

### 输入与执行

触发及资料：待付款账单、邮箱或上传发票、账本、现金数据、付款权限。

输入检查（研究建议）：

- 汇集发票、供应商主数据、采购和收货记录、已入账记录及明确的账本目标。
- 确认现金截至日期、近期工资与到期义务、币种；逐笔列出不可读字段及重复或贷项。

上游执行顺序（归纳）：

1. ap-processor 读票与分类
2. 确认一：未付款账单入账
3. cash-flow-snapshot 检查现金
4. 准备付款列表
5. 确认二：付款决定
6. month-end-prep 整理本次记录。

交付物：现金位置、拟付总额、供应商与到期日、折扣或停供风险、明确的审批范围；按偏好输出 HTML、文档等。

### 控制边界

- **提示词约束｜上游文字要求：** 两次独立批准、现金检查居中、不得自动付款或扩大列表，都是 Skill 的明确指令。allowed-tools 元数据和连接器清单不等于经过验证的双审批系统。
- **程序与工具｜静态证据及边界：** 已核对 pay-the-bills 与 ap-processor 文本，未发现其中附有执行两道门的本地状态机代码；远端账本、Ramp 与付款服务实现没有在本次研究中审计。
- **系统强制控制｜建议补齐，未验证：** 建议入账和付款使用不同权限及状态转换；服务端将第二次审批绑定到发票 ID、金额、币种、收款方与账户、日期和列表摘要，变更后重审。付款用幂等键和回执查重，不能靠聊天历史判断已付。

### 异常与人工处理

以下分支是根据上游规则组织的落地建议；不是已执行的故障演练。

| 触发条件 | 处理与停止条件 |
| --- | --- |
| 无账本写入能力、只读连接或不支持未付款账单对象 | 交付编码导入文件与人工清单，不伪造入账成功；连接品牌名称不能证明写入能力。 |
| 发票要求改付新账户或金额不可读 | 暂停受影响项目，由负责人使用原留存联系方式核验；不按发票里的新联系方式自证。 |
| 缺现金数据或付款返回超时 | 前者在摘要顶部注明未核现金；后者标结果未知，先查付款状态再决定后续，不能盲目重付。 |

**人工审批｜上游规定：** Gate one 明示数量、总额、账本及写为未付款账单；Gate two 在现金情况展示后批准或缩减付款清单。两门不得合并，重复历史批准也不是本次同意。供应商邮件另需批准。

**人工审批｜建议落地：** 老板或授权财务人员分别确认两门；第二门绑定精确付款对象和金额。建议现金未核实时进入明确的例外审批；这是增强方案，上游允许醒目标注缺口后提出清单。

### 验收标准（建议，未执行）

- [ ] 模拟只批准入账时，不产生付款；第二次批准后新增发票或更改账户必须重新审查。
- [ ] 重复发票、贷项与账号变更样本分别呈现；现金不足或缺失不被隐藏。
- [ ] 系统集成沙箱测试未授权调用被拒、重复提交不重复付款、超时后可查回执；这些均为待执行验收，不是本研究已通过结果。

### 相比直接对话的价值（待实验验证）

- **直接对话基线：** 直接对话可以整理账单，但常把编码和付款混成一次笼统请求。
- **可复用增量：** 把入账、现金判断和付款决定拆开，清楚展示老板实际批准的内容，减少重复整理与错误承诺。
- **成立条件与局限：** 最大的安全收益只有在系统真的执行审批与幂等时才成立；提示词不能独立承担付款控制。
- **建议衡量：** 比较重复项漏检、批准范围偏离、现金缺口漏报和人工准备时间；未经授权付款次数必须单列，不能用平均节省时间抵销。

## W15 · 企业搜索：追溯决策

**具体业务：** 查清某次技术迁移最后采用哪个方案，区分早期讨论、正式决定和后续变更。

### 输入与执行

触发及资料：决策、状态、文档、负责人或事实问题；来源范围、时间条件与连接权限。

输入检查（研究建议）：

- 明确项目实体、所问的是决策还是当前状态、时间边界和允许搜索的来源。
- 记录各来源可用性、文档日期与作者权限范围，不把无权限视为没有记录。

上游执行顺序（归纳）：

1. 判断问题类型
2. 拆关键词 / 实体 / 时间
3. 生成各来源查询
4. 并行检索
5. 合并去重和排序
6. 综合回答。

交付物：直接回答、支持证据、来源日期和位置、冲突说明及信息置信程度；不只是按系统堆搜索结果。

### 控制边界

- **提示词约束｜上游文字要求：** 查询拆解、并行搜索、权威与时效排序、逐项引用和冲突保留是文本策略；权重表不是已执行的排序算法。
- **程序与工具｜静态证据及边界：** 本次核对的 search-strategy 与 knowledge-synthesis 未附搜索调度器或确定性评分实现；具体搜索由连接器完成。
- **系统强制控制｜建议补齐，未验证：** 建议检索服务在返回结果前实施文档权限过滤，保留查询与来源版本；必要时校验引用目标仍存在，不能让模型自行决定可公开范围。

### 异常与人工处理

以下分支是根据上游规则组织的落地建议；不是已执行的故障演练。

| 触发条件 | 处理与停止条件 |
| --- | --- |
| 实体有多种解释 | 提出一个聚焦澄清问题，或分别列出不同项目结果，避免错误混合。 |
| 来源不可用、限流或全无结果 | 披露缺口、扩大合法查询或建议稍后重试；不能绕过权限，也不能把无结果当否定事实。 |
| 旧方案与新决定冲突 | 按日期、决策权和问题类型解释，保留差异，不因新消息更近就一律覆盖正式政策。 |

**人工审批｜上游规定：** 普通检索没有统一审批门；歧义需要澄清，回答要求可归因。

**人工审批｜建议落地：** 信息访问由系统授权；决定归属有争议时由负责人确认。对外转发或扩大分享范围独立于检索授权。

### 验收标准（建议，未执行）

- [ ] 每个关键事实有能定位的来源与日期，讨论、决定和后续状态分开。
- [ ] 冲突材料样本保留不同结论；缺来源样本说明覆盖不足。
- [ ] 在集成环境用受限账号检索，未授权文档不应进入模型上下文；该权限测试本次未执行。

### 相比直接对话的价值（待实验验证）

- **直接对话基线：** 直接对话拿到全部资料后可以综合，但用户常要自己找齐材料。
- **可复用增量：** 复用跨来源查询、去重和证据综合方法，减少查找与人工比对。
- **成立条件与局限：** 没有连接器时价值主要在整理材料；引用存在也不保证结论正确。
- **建议衡量：** 比较错误归因、遗漏冲突、无引用事实、检索覆盖及找到可用依据的时间。

### 异常与人工处理

以下分支是根据上游规则组织的落地建议；不是已执行的故障演练。

| 触发条件 | 处理与停止条件 |
| --- | --- |
| 查看器不可用或 UUID 不匹配 | 报告未写入，恢复正确会话再操作，不创建多个查看器后假设用户看到同一份。 |
| 表单名称不清、坐标偏移或文字未找到 | 查看页面与边界框，核对视觉标签和页码；不能猜测字段或成功位置。 |
| 导出失败或要求认证签名 | 保留原文件，明确未生成有效副本；说明视觉签名能力范围。 |

**人工审批｜上游规定：** 协作批注明确先展示方案、获批后添加；表单值按视觉标签询问或上下文推断后展示确认。签名图流程要求图像路径、位置和截图，但未定义认证签署。

**人工审批｜建议落地：** 用户核对具体批注批次、字段值和签名位置；最终交付以导出副本为对象，若另有签署授权流程则独立执行。

### 验收标准（建议，未执行）

- [ ] 批注落在正确文档、页码和位置，表单值与用户要求一致。
- [ ] 截图检查后重新打开导出 PDF，确认批注、表单与页面保存完整。
- [ ] 工具失败时不声称已写入；图像签名明确标为视觉放置，不标为认证数字签名。

### 相比直接对话的价值（待实验验证）

- **直接对话基线：** 直接对话可建议批注，但纯文本难以共同确认实际位置与保存效果。
- **可复用增量：** 工具化查看器提供可视化反馈、共同修订和文件导出，这是超出纯文本模板的交互增量。
- **成立条件与局限：** 价值依赖外部 PDF 服务实际可用；本研究未验证其运行和签署能力。
- **建议衡量：** 比较错页错位、字段映射错误、导出内容丢失和人工定位时间。
