# 项目维护指南

## 编号与目录

- 使用三位编号与小写英文 slug：`001-project-name`。
- 新编号取已有最大编号加一；保留归档条目，不复用编号。
- 首页和演示门户按编号升序展示，与 JSON 中的录入顺序无关。
- slug 尽量固定，避免已发布演示与文档链接变化。
- 研究状态为 `待研究`、`研究中`、`已完成`、`已归档`。

## 新增一个项目

1. 确认原仓库链接、研究目标和上游许可证。
2. 将 `templates/project/` 复制到 `projects/001-example/`，按实际下一个编号命名。
3. 修改项目 README、研究记录与实践代码；删除或替换不适用的提示。
4. 在根目录 `projects.json` 的 `projects` 数组中添加元数据：

```json
{
  "id": "001",
  "slug": "example",
  "title": "项目名称",
  "summary": "一句话说明项目能做什么，以及对我们的价值。",
  "highlights": {
    "capability": "已有能力或本次研究产出。",
    "principle": "支撑能力的关键机制与实现方式。",
    "value": "对我们的复用价值或适用场景。",
    "boundary": "未验证事项、运行条件或尚待实现的扩展。"
  },
  "repository": "https://github.com/owner/repository",
  "status": "待研究",
  "image": null
}
```

5. 有截图后，将 `image` 改为实际存在的项目内相对路径，如 `assets/cover.png`。
6. 执行 `python scripts/catalog.py --update-readme`，自动更新首页表格、图片展示和本地演示门户。
7. 执行 `python -m unittest discover -s tests` 与 `python scripts/catalog.py --check`，检查差异后提交。

不要手动编辑首页 `PROJECT_INDEX` 标记之间的内容；该区域由元数据生成。标记之外的介绍和导航可自由维护。

### 首页摘要怎么写

- `summary` 用一句简短的话连接“能力 + 价值”，用于表格上方的项目速览、图览说明和门户卡片，不写 Markdown 格式。
- `highlights` 将详细摘要拆为 `capability`（能力）、`principle`（原理）、`value`（价值），可补 `boundary`（边界）；生成器统一添加加粗标签和表格内换行。字段值保持单行纯文本，无需手写 `<br>` 或 `**`。
- 新增项目按上述结构填写；兼容已有的仅 `summary` 条目。提供 `highlights` 时，能力、原理与价值三项必须齐全。
- 能力写已经存在的内容；复用设想使用“可借鉴”“可扩展”等措辞；未验证与未实现的关键部分写入边界，避免把研究完成等同于产品已落地。
- 源仓库链接自动显示 URL 中的真实仓库名，保留大小写；网站研究可用 `source_name` 指定真实网站名称，缺省显示域名。不要以本地研究页标题替代上游名称。
- 首页按“项目速览 → 详细索引 → 可展开图览”生成；编号、链接与图览继续来自同一份元数据。

### 网站研究来源

研究对象是网站且未确认公开源码时，使用 `"repository": null` 并提供 `"source_url": "https://example.com/page"`。来源链接须为无凭据的 HTTPS URL；括号使用 URL 编码。README 中明确记录“未确认公开仓库”、授权情况与访问日期，不编造 GitHub 地址或开源许可证。已有开源项目继续使用原来的 `repository` 字段。

## 子项目建议结构

```text
projects/001-example/
├── README.md       # 介绍、截图、复现说明、研究结论
├── notes.md        # 研究过程与实验记录
├── assets/         # 封面与截图
├── app/            # 实践源码，各项目独立管理依赖
└── web/            # 可选的静态导出；有 index.html 才创建演示入口
```

演示目录在生成门户时会整体复制，因此只放可公开访问的文件。图片由 `image` 字段按需复制；笔记与 `app/` 源码不进入 Pages 站点。仓库本身是公开的，已提交的文件仍可在 GitHub 上访问。

## 制作与验证后的清理

视频、素材制作和渲染验证的收尾必须包含临时文件清理，不将可重建的大缓存长期留在归档项目中。

1. 制作时记录本轮生成的 bundle、编译缓存、逐帧中间文件和验证副本的精确目录；临时编写的源码、配置和有保留价值的证据应及时迁入正式源码或研究资料目录。
2. 确认任务已结束、成片与所需证据已保存，再清理本轮可重建目录；保留源码、依赖锁文件、配置、原始素材、成片、研究与返修记录，以及子项目 `web/`。重新生成成本较高的逐帧结果先核对成片和证据完整性，再决定是否回收。
3. `.cache/`、`exports/`、上游副本与本地运行环境可能混有源码、配置、原件或研究证据，不能只按目录名整批删除。清理前检查解析后的绝对路径及目录内链接，范围必须留在预期目录内；不触碰其他运行任务的输出。
4. `python scripts/catalog.py --check` 只校验索引，不生成或修改 `_site/`。需要发布或完整路径预览时执行 `python scripts/catalog.py`；`--update-readme` 仍会同步索引并生成站点。完成预览、验证或发布打包后，回收不再使用的根目录 `_site/`，保留各项目的 `web/`。
5. 完成仓库校验，记录本轮清理范围和释放空间；交付前确认未留下大体积临时打包。此前确认可回收的目录不需要重复请求清理许可，但每次执行前仍应复核用途与路径。

## 归档与许可证

停止研究时将状态设为 `已归档`，保留已有编号、结论和来源。不要将上游许可证替换成总仓库的许可证；引入第三方代码或素材时，应逐项确认授权并保留声明。
